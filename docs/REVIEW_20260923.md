## 2. 방향 — 발견한 문제 (우선순위순)

### ① [높음] 학습 데이터가 바뀌어 73.3 과의 비교가 오염된다

목표 "라이브 70"은 사내 73.3 대비다. 그런데 학습 데이터가 (공간 부족으로) Sensenova 로 바뀌었다.
우리가 66 을 찍으면 그게 **스트리밍 비용**인지 **데이터 차이**인지 가를 수 없다.

- 스트리밍 평가의 `halving` vs `uniform_oracle` 차이는 **키프레임 선택 비용(손실②)**만 분리한다.
- **인코더 비용(손실① VGGT→스트리밍)**은 같은 데이터로 돌린 오프라인 VGGT 팔 없이는 분리 불가.

→ 필요한 정보: **73.3 의 학습 데이터에 Sensenova 가 들어 있나, 영상 데이터는 무엇이었나**
(`QUESTIONS_FOR_EXISTING_SYSTEM.md` P0-2). 답에 따라 VGGT 대조군을 앞당길지 정한다.

### ② [높음] 학습은 이미지, 주지표는 영상

Sensenova 는 레코드당 1~28장, 대부분 1~8장의 다시점 이미지다. VSI-Bench 는 1~2분 워크스루 영상이고
**개수 세기·방 크기·등장 순서·경로 계획**은 영상 전체를 통합해야 풀린다.
평가를 이미지 모드로 맞춰 입력 분포는 일치시켰지만, **32장짜리 긴 시퀀스를 학습에서 본 적이 없다.**

→ 영상 유래 학습 데이터가 필요하다. 공간이 문제라면 영상 대신 **프레임을 이미지 시퀀스로 저장**
(예: VSI-590K 어노테이션 + 씬당 32프레임 JPEG)하면 mp4 원본보다 훨씬 작다. 사용 가능한 영상 데이터가 뭔지 확인 필요.

### ③ [높음] VideoMME 회귀 게이트 측정이 오염될 수 있다

채택 게이트 2번(VideoMME 회귀 ≤ 1.0)은 비스트리밍 lmms-eval 경로(`auto_geometry`)로 잰다.
이 경로는 영상을 **비디오 모드**(2프레임→1블록, 기하 2장 평균)로 넣는데, 프로젝터는 Sensenova 로
**이미지 모드만** 학습한다. 그러면 게이트는 "일반 능력 회귀"가 아니라 "프로젝터가 처음 보는 입력"을 잰다.

→ 게이트를 재기 전에 비스트리밍 평가도 이미지 모드 키프레임 경로로 통일해야 한다 (S2 전에 필요).

### ④ [중간] 최종 기하 상태가 LLM 에 안 들어간다 — 테제와 구현의 간극

테제: "LLM = 키프레임 비전 토큰 + **전 구간 기하 상태**". 구현: 키프레임 **시점의** 기하 토큰만 주입한다.
CUT3R 의 고정 크기 재귀 상태(설정 기본 324 토큰 — 체크포인트마다 다를 수 있다)는 질문 시점에 LLM 에 한 번도 노출되지 않는다.
키프레임 사이 프레임들은 **다음 키프레임 토큰을 통해 간접적으로만** 영향을 준다.

개수 세기·방 크기처럼 전 구간 통합이 필요한 문항, 그리고 OVO-S L4(allocentric)가 바로 이 부분이다.
**SpatialStack(VGGT) 대비 우리만의 차별점이 여기서 나온다** — 오프라인 VGGT 에는 "스트림 전체를 압축한
상태"라는 개념 자체가 없다.

→ S1 베이스라인 다음의 첫 아키텍처 실험 후보: 최종 상태 토큰을 풀링·투영해 **장면 메모리 토큰 ~64개**로
프롬프트에 넣기.

### ⑤ [중간] 해상도 예산이 73.3 과 다를 수 있다

지금 이미지당 최대 128×32×32 픽셀(≈362², LLM 토큰 ≤128개). 73.3 의 해상도는 모른다(질문 P0-6).
더 높았다면 스트리밍과 무관하게 점수를 잃는다. `--max-pixels` 로 조절 가능.

### ⑥ [중간] CUT3R 이 학습 병목일 수 있다

샘플당 이미지 5~8장을 fp32 CUT3R 로 인코딩한다. 스모크 B 의 `geom ms` 가 `fb ms` 보다 크면
bf16 추론(재구성 품질 확인 후)을 검토한다.

### ⑦ [낮음] 기타

- 멀티턴: 과거 턴에도 빈 think 블록을 넣는다(감독 토큰의 조건을 추론과 맞추려고). 공식 템플릿과 과거 턴 렌더링이 다르다.
- 인코더 베이크오프 미착수. Anchor3R·LingBot-Map 은 잠재 토큰 노출 방식이 문서화돼 있지 않아 연동 리스크가 있다.
