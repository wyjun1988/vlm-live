# Live3R, 2026-09-23 → 2026-10-15 — what was done and what was found

The question: can a small VLM (Qwen3.5-4B) answer spatial questions about a video **as it streams** - frames arriving
at ~1 fps, no knowledge of the video's length, the answer within a second - at the level of the in-house offline
system (VSI-Bench 70.83), with its general ability kept? The answer so far: **yes, and above it - 72.7 on VSI-Bench
under live frame selection**, with a design simpler than the one we started from. This file is the record; the
details live in the documents it points to.

## 3. The live design, as it stands

- **Model:** the plain SFT arm of run 3 (LoRA r16 on the LLM, long side 512, the `live` mix, no CoT, no geometry).
- **Frames:** every frame at 1 fps through the vision tower into a cached prefix; when more than 128 are held, halving
  over the 1 fps grid keeps them evenly spread over everything seen so far - nothing depends on the video's length.
- **Question time:** the question tokens on the cached prefix (170 ms to the first token on the gated prototype;
  the 128-frame plain design still to measure, re-prefill after halving included).
- **CUT3R:** out of the VSI loop. As tokens in the LLM input it adds −0.2; as text measurements ≤ 0 on the trained
  model. It stays only for what frames cannot give - metric outputs, scene memory beyond the cap - to be justified
  on its own.
- **Still to do before a demo:** the latency of this design; the serving session's visual-token cap (16,384 today,
  below 128 frames × 192 tokens); the voice front-end's live numbers.

## 4. What is new relative to the in-house system

| | in-house (reference) | ours |
|---|---|---|
| when the frames are chosen | after the whole video, 32 uniform | as the video streams, causal halving over a 1 fps grid; budget = the cap |
| frames to the LLM | 32 | up to 128 at 1 fps (+2.2 over 32 on the trained model) |
| CUT3R | tokens fused into the LLM input | not in the VSI loop; as a measurement engine it was worth +2.7-3.5 zero-shot and ≤ 0 after SFT |
| training data | 2.03 M incl. six CoT sets | 1.42 M without CoT - the same score (71.3 vs 70.83): CoT data is not needed for a non-thinking model |
| data hygiene | one VSI-Bench scene in SPAR | excluded; marks drawn by our code; the training text in the evaluation form |
| evaluation | single numbers | video-level paired bootstrap intervals, shuffled-geometry control, learning curve, a general-ability gate |
| question handling | benchmark templates | a reader that types the question (Korean read as is) and routes measurements - the base of the voice front-end |
| answer latency | offline | cached prefix, question-only TTFT |
| what we learned about their design | — | gated token fusion ≈ 0 at this data scale, confirmed in a controlled same-data run; 128 frames are enough; their training speed gap was the Gated DeltaNet kernels (see §6) |

## 5. Tried and rejected (each measured, each kept in the code off by default)

Our own starting thesis - geometry tokens fused into the LLM (deepstack in run 1, the reference's gated input fusion in
run 3) - did not pay: −1.6 and −0.2. Also rejected: the top-down map image (−0.3), the object map as text (−13.7 /
−9.9), the model's own cognitive map (−4.8), measured object size (the category prior wins), windowed state resets,
per-frame scale anchors (−8.3), Utonia counts and floor area (worse than the model), merging duplicate instances by
position, measured frames as extra CUT3R inputs, thinking at question time, always-on facts, and - on the trained
model - every text measurement (room facts −0.7 … stack −1.0). The lessons are L1-L8 in `docs/BRAINSTORM.md`.

## 6. Infrastructure findings worth keeping

- **Training speed.** transformers runs Qwen3.5's 24 Gated DeltaNet layers on a pure-torch chunk loop unless fla's
  kernels are present; since fla 0.5 those kernels are the separate package `fla-core`, which a `--no-deps` install
  skips - run 3 trained at 2.1 samples/s per 8 H100 (the reference 6.48). Measured: fla 4.9× / 7.2× faster at 4k /
  12k tokens, numerics identical. transformers 5.18 picks fla up by itself at import time (no device check), so the
  CPU test suite must block it (`tests/conftest.py`). `docs/SERVER_RUN4_PREP.md`.
- **The gate smoke** (`--limit 4`) broke lmms-eval's VSI aggregation (a missing question type → KeyError); the smoke
  now runs MMStar only. The gate's base reference answers without the format line and is format-handicapped.
- **Two prompt forms:** training records put "\n" after every image block, the evaluation prompt never did;
  `data.image_newline: false` trains in the evaluation form, and the trained form evaluates lower anyway.
- **Server orchestration:** one script per run, roles claimed on the shared volume, resumable training, sharded
  evaluation, a report regenerated at every step, one bundle to send back (`scripts/server_run3.sh`).
- **M2 specifics:** transient MPS failures in long sequential runs ("!!!!" answers, an all-"wall" segmentation) -
  freed caches, warnings and a CPU redo; never two heavy MPS jobs at once.
