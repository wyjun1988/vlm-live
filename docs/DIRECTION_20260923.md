## 3. 핵심 아키텍처 결정 — 이중 레이트

```
입력 30fps ──┬─→ 기하 인코더   5~10fps 인제스트 (상수 상태, 전 구간을 압축 보유)
             └─→ 키프레임 선택  LLM 비전 토큰은 예산 N장만 (인과적 선택)
                                     ↓
                    LLM = 키프레임 비전 토큰 + 전 구간 기하 상태
```

**근거**: 기하 상태가 전 구간을 이미 압축해 들고 있으므로 LLM이 모든 프레임의 비전 토큰을
볼 필요가 없다. 오프라인 VGGT 는 "본 프레임 = 추론에 쓰는 프레임"이라 이 분리가 불가능하다.
**우리 쪽에만 있는 구조적 여유**고, 3.3점을 여기서 번다.

동시에 이게 손실 ②를 정면으로 건드린다 — 오프라인은 영상 길이를 알고 균등 추출하지만
라이브는 흘러가며 정해야 한다.

## 5. "스트리밍 제약"의 정의 (하니스가 강제한다)

라이브를 주장하려면 아래를 **깨지 않았음이 기계적으로 증명**돼야 한다.
사람이 안 깼다고 믿는 걸로는 부족하다 — 실수로 깨기 너무 쉽다.

1. 프레임은 **시간순 1패스**. 되돌아가 다시 인코딩 금지
2. 기하 상태 크기 **상수**
3. 키프레임 선택은 **인과적** — 미래 프레임도, **영상 총 길이도** 못 본다
   (`len(video)` 를 아는 순간 균등 샘플링이 가능해지고 그건 오프라인이다)
4. LLM 비전 토큰 **예산 상한** 고정
5. 질문 도착 후 **프레임 재인코딩 금지** (캐시 뒤에 질문만 붙인다)

→ `src/live3r/eval/streaming.py` 의 감사기(auditor)가 위반 시 **예외를 던진다.**
